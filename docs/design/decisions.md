# Design decisions (D8)

Decisions for the Pi monitor app, agreed during the design phase. Mirrored on the Miro board (Kanban Software, card D8).

On 2026-10-27 the firmware team delivered the UART interface draft ([Research/STM32_Pi_UART_Interface_Draft_V1.docx](../../Research/STM32_Pi_UART_Interface_Draft_V1.docx), review draft 0.4, protocol version 0x02, called **UART draft** below). Decisions it changed are marked "Revised (UART draft)".

| ID | Decision | Refs | Status |
|---|---|---|---|
| DD-01 | Diagrams are Mermaid sources in `docs/design/` (source of truth), mirrored to Miro for review. | S1 | Agreed 2026-10-27 |
| DD-02 | Two processes: a headless core service (systemd: UART, fan control, database, web dashboard server) and a separate display app. A UI crash never stops fan control or logging. Display ↔ core over a Unix socket. | S6, S7.4, S8, S9 | Agreed 2026-10-27 |
| DD-03 | Touchscreen UI is native Rust, no browser/kiosk. The S9 web dashboard is still served by the core service for laptops on Ethernet. | S1.2, S8, S9 | Agreed 2026-10-27 |
| DD-04 | Storage tiers per S10: 1 s data RAM-only (1 h ring buffer), 10-min min/avg/max records on disk, daily records on disk. No raw 1 s data on disk except fault snapshots. | S10.2–S10.4, S10.8 | Agreed 2026-10-27 |
| DD-05 | Wide tables: one column per signal (fixed 4S3P signal set). | S10.3, S10.11 | Agreed 2026-10-27 |
| DD-06 | Timestamps stored as UTC ISO 8601 text, fixed format `YYYY-MM-DDTHH:MM:SS.sssZ` (sorts lexically); shown in local time. Replaces the earlier integer-ms idea. | S10.10 | Agreed 2026-10-27 |
| DD-07 | Fault snapshot written in two stages: fault record + 60 s before immediately (≤ 1 s), the 60 s after appended every ~10 s. A fault inside an open window extends that snapshot. | S10.5, S10.6 | Agreed 2026-10-27 |
| DD-08 | MCU sends cumulative Ah/Wh counters (charged and discharged) in telemetry; the Pi only takes differences, so Pi reboots lose no energy counting or SoH measurement. **Not in the UART draft** (telemetry has no SoC and no counters); to request together with SoC (D9); proposed layout in [firmware-requests.md](firmware-requests.md). | S5, S10.3, S10.9 | **Open: to agree with firmware** |
| DD-09 | Daily record is written at 00:00 local time for the finished day. "Compaction" = deleting 10-min records older than 30 days. DST days (23/25 h) handled explicitly. | S10.4, S10.7 | Agreed 2026-10-27 |
| DD-10 | Each aggregate stores a `sample_count`; daily averages are weighted by it; graphs show gaps. | S10.3, S10.4, S9 | Agreed 2026-10-27 |
| DD-11 | No records are timestamped until the clock is valid (NTP or RTC); a "time invalid" event is logged. | S10.10, S10.16 | Agreed 2026-10-27 |
| DD-12 | SQLite WAL with `synchronous=FULL` (write load is tiny) to meet "power loss loses at most the last record". | S10.1 | Agreed 2026-10-27 |
| DD-13 | The 1 h RAM buffer is not persisted; live graphs start empty after a reboot. | S10.2 | Agreed 2026-10-27 |
| DD-14 | One HTTP/JSON API (axum) for both the touchscreen app and the laptop dashboard: served on a Unix socket for the display, on TCP for laptops. The display app has no database access. | S8, S9 | Agreed 2026-10-27 |
| DD-15 | A single `db_writer` thread owns the only SQLite write connection; all other tasks send it messages (mpsc). Readers use separate read-only connections (WAL). | S10.1 | Agreed 2026-10-27 |
| DD-16 | Fan behaviour on BMS comm loss (OFFLINE) comes from the MCU CONFIG: `fan_offline_action` 1 = hold last duty, then off after `fan_offline_ms`; 2 = 100 % while OFFLINE; 0 = undecided (Pi then runs 100 %, see DD-28). The policy is owned by the MCU/system team, not the Pi. | S6, S8.12, UART draft §6–7 | Revised (UART draft) |
| DD-17 | Crash policy: `panic = "abort"`, systemd `Restart=always` + `WatchdogSec`; any task failure restarts the whole core. No task-level restarts. While the core is down the heartbeat stops, so after > 5 s the MCU raises E11 and switches charging off (UART draft §8). Fan behaviour while the core is down depends on the fan controller hardware: **open** (D10). | S3.8, S6, S7.4 | Agreed 2026-10-27 (fan fallback open) |
| DD-18 | Live data is pushed to display and dashboard with Server-Sent Events; actions use normal HTTP requests. | S8, S9.4 | Agreed 2026-10-27 |
| DD-19 | Touchscreen UI toolkit: Slint. | S1.2, S8 | Agreed 2026-10-27 |
| DD-20 | One `event` table for faults, warnings and system events (`kind` = FAULT / WARNING / SYSTEM); the fault log and event log pages are filters on it. | S9.9, S9.10, S10.5 | Agreed 2026-10-27 |
| DD-21 | A fault snapshot (±60 s of 1 s data) is taken for every `FAULT` event, i.e. every Protection, Latched protection and Critical code (DD-33); Warnings get no snapshot. | S10.6 | Agreed 2026-10-27 |
| DD-22 | Every MCU fault event stores all signal values of the frame that raised it (TELEMETRY or FAULT_UPDATE carry the complete measurement set), plus its validity. These are the values *at report*, not the exact trip values (UART draft §9). | S9.9, S10.5 | Revised (UART draft) |
| DD-23 | Retention: 10-min records 30 days; daily records, events and SoH kept forever; snapshots deleted oldest-first only when the DB passes `DB_SIZE_SOFT_LIMIT` (proposal 150 MB), logged as an event. No automatic `VACUUM`. | S10.5, S10.7, S10.8 | Agreed 2026-10-27 |
| DD-24 | Battery configuration, protection limits, fan tables, fan fault and offline parameters and timeouts come **only** from the MCU CONFIG message; the Pi keeps no copy of its own. Runtime settings (PIN hash, wrong attempts, lock) live in the DB `setting` table. The TOML file in `/etc/bess/` holds Pi-only settings (serial device, ports, DB limits, PIN rules, backup path, cloud). | S2.1–S2.4, S6, S9.12 | Revised (UART draft) |
| DD-25 | Cloud upload keeps a watermark per table (last acknowledged key) instead of a queue table; events whose `cleared_ts` changed are re-sent by `id`. | S10.15 | Agreed 2026-10-27 |
| DD-26 | Core has a `uart_tx` task: HEARTBEAT every 1 s, CONFIG_REQUEST every 1 s in WAIT_CONFIG, CONFIG_ACK after validation, FAULT_RESET on user action. The heartbeat carries the accepted `boot_counter` + `config_revision` (both 0 before acceptance) and is only sent while `link_supervisor` and `fan_controller` are alive, so the MCU's E11 also covers a hung Pi app. Until it gets an identity-matched heartbeat the MCU keeps charging inhibited. | S2.4, S3.6, S3.8, UART draft §8 | Revised (UART draft) |
| DD-27 | BMS link states OFFLINE / WAIT_CONFIG / ONLINE, 3 s (`pi_data_timeout_ms`) on the monotonic clock from the last valid frame. Telemetry carries `boot_counter` and `config_revision`; a change of either sends the Pi back to WAIT_CONFIG. ONLINE needs a CONFIG that passes validation, a sent CONFIG_ACK (accepted) and telemetry with the same identity. After a short loss with unchanged identity the Pi resumes ONLINE without re-reading. | S2.4, S5, S8.12, UART draft §4, §8 | Revised (UART draft) |
| DD-28 | Before the first valid CONFIG (no fan table yet) and while `fan_offline_action` = 0 (undecided), the fans run at 100 %. Without a CONFIG there is no `fan_offline_ms`, so they stay at 100 % until a CONFIG arrives. | S2.4, S6 | Revised (UART draft), agreed 2026-10-27 |
| DD-29 | While OFFLINE, a last-known ESTOP or FAULT state stays shown (with the comm-lost banner); otherwise OFFLINE is shown. | S8.9, S8.10, S8.12 | Agreed 2026-10-27 |
| DD-30 | `core_state.last_alive_ts` written every 60 s; each start logs `LOG_GAP` marked `clean` / `crash` / `power loss`. | S10.17 | Agreed 2026-10-27 |
| DD-31 | Clock validity read from `chrony`; events from before the clock was valid wait in a RAM queue (max 100); clock steps > 2 s logged as `TIME_ADJUSTED`. | S10.10, S10.16 | Agreed 2026-10-27 |
| DD-32 | Display shows "Monitor service restarting…" when the core is gone, separate from "BMS communication lost". | S7.4, S8.12 | Agreed 2026-10-27 |
| DD-33 | Event `kind` follows Table A severity: Warning → `WARNING`; Protection, Latched protection, Critical → `FAULT` (all get a snapshot, DD-21). Banner/list order Critical > Protection > Warning, then lowest code (S3.22). | S4.1, S10.6 | Agreed 2026-10-27 |
| DD-34 | Every TELEMETRY and FAULT_UPDATE frame carries the complete 32-bit fault bitmap (bits 0–18 = E01–E19). `event_detector` processes every frame in arrival order and raises/clears from the difference with the previous bitmap, so short faults reported only in FAULT_UPDATE frames are logged too. Pi-local E12 is merged in. | S5.8, S10.5, UART draft §4–5 | Revised (UART draft) |
| DD-35 | The fault log's "measured value" is picked from the stored frame values (DD-22) by a `trigger_signal` column per code in the Table A source file, and labelled as the value at report. | S4.1, S9.9 | Revised (UART draft) |
| DD-36 | `event` has `fw_version` (from CONFIG `fw_major.minor.patch`), `app_version`, `boot_counter` and `config_revision` columns. | S1.8, S1.12, UART draft §9 | Revised (UART draft) |
| DD-37 | On core start, reconnect and MCU restart, open events in the DB are reconciled with the first frame's fault set; nothing is raised or cleared while OFFLINE. | S9.9, S10.5 | Agreed 2026-10-27 |
| DD-38 | Fault reset per UART draft §8: FAULT_RESET with a nonzero `request_id` plus target `boot_counter`/`config_revision`; RESET_ACK result 0 accepted, 1 fault still active, 2 identity mismatch, 3 not ready. 2 s timeout, no automatic retry. The last `request_id` is kept in `core_state` so a restarted core never reuses one. Request and result are both logged. Reset source in telemetry (BMS button) is not in the draft: still optional. | S3.6, S9.12 | Revised (UART draft) |
| DD-39 | E12 FAN_FAULT is detected, shown and logged only by the Pi; not sent to the MCU (bit stays 0 in MCU frames). Detection: fan duty > 0 and RPM < `fan_speed_min_pct` of the table's expected RPM for `fan_fault_ms`; disabled (shown "calibration unavailable") while the CONFIG RPM calibration flag is clear. | S6, S3.7, UART draft §5, §7 | Revised (UART draft) |
| DD-40 | The `protocol` crate implements the UART draft: 115200 8N1, header `AA 55`, version 0x02, little-endian, CRC-16/CCITT-FALSE over version…payload, exact length per message id, resync after bad input, bounded buffers; bad frames counted (S5.9). The reference frames in the draft are unit tests; C-generated frames are still required (S5.11). | S5.1–S5.11 | Agreed 2026-10-27 |
| DD-41 | Telemetry `validity` bits: an invalid or absent field is stored as NULL, shown as "N/A" and left out of min/avg/max (DD-10 `sample_count` counts frames). NTC4 presence from CONFIG `ntc_present_mask`. | S8, S10.3, UART draft §4 | Agreed 2026-10-27 |
| DD-42 | E-STOP state: `fan_controller` commands the fans off; this overrides every other rule (E7.7). E05/E17 still force 100 % in all other states. | E7.7, S6 | Agreed 2026-10-27 |
| DD-43 | Every CONFIG the Pi validates is stored in a `mcu_config` table (identity, firmware version, raw 190 bytes, accepted/rejected status), for System info (S9.11) and to interpret old data. | S2.4, S9.11 | Agreed 2026-10-27 |
